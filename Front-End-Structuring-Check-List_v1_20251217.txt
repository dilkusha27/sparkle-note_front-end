🧱 1. 역할 분리 / 모듈성

UI 컴포넌트가 비즈니스 로직이나 API 호출을 직접 수행하고 있는가?

하나의 컴포넌트가 하나 이상의 변경 이유를 가지고 있는가?

공통 로직이 복사·붙여넣기로 사용되고 있는가?

UI 변경이 로직 변경으로 이어지는 구조인가?

기능 단위로 분리된 코드를 다른 프로젝트로 옮겨도 바로 쓸 수 있는가?

🔗 2. 의존성 관리 / 결합도

UI 레이어가 비즈니스 규칙을 직접 알고 있는가?

한 도메인의 내부 구현을 다른 도메인이 직접 참조하는가?

특정 기능 수정이 여러 도메인 폴더에 영향을 주는가?

전역 상태가 “편해서” 사용되고 있지는 않은가?

특정 파일 하나가 여러 기능의 진입점 역할을 하고 있는가?

🧭 3. 경계 명확화 / 응집도

파일명과 폴더 위치만 보고 역할을 추측할 수 있는가?

하나의 폴더 안에 서로 다른 관심사의 코드가 섞여 있는가?

기능 수정 시 “어디를 고쳐야 할지” 바로 떠오르는가?

pages / features / hooks / shared의 책임이 겹치지 않는가?

임시 파일이나 실험 코드가 구조 안에 남아 있지는 않은가?

🔧 4. 변경 비용 최소화

작은 요구사항 변경이 예상보다 많은 파일 수정을 요구하는가?

공통 컴포넌트 수정 시 다른 화면이 깨질까 두려운가?

조건 분기가 늘어날수록 코드 이해 난이도가 급격히 올라가는가?

상태 변경 지점이 분산되어 추적이 어려운가?

“이건 건드리기 무섭다”라고 느끼는 코드가 존재하는가?

🔍 5. 의도 드러내기 / 가독성

코드 구조만 보고 사용자 흐름을 설명할 수 있는가?

기술 용어보다 서비스 개념이 코드에 드러나는가?

구조를 설명하기 위해 말이 길어지는가?

네이밍이 동작과 목적을 동시에 설명하고 있는가?

신규 인원이 구조 설명 없이 작업을 시작할 수 있을 것 같은가?
